What the VGS proxy actually does to your traffic

Very Good Security sits in the network path in front of your servers. Card numbers get swapped for aliases on the way in and swapped back on the way out, so your own systems never hold the real values. Type a card below, send it through, and watch what each hop sees.

    A VGS route is a host match plus a list of filters. Each filter has conditions (path, content type), a field selector (here JSONPath), and an operation: REDACT on the way in, REVEAL on the way out.

    What changes in your code
    
        
    Inbound: the form posts to your vault's URL instead of your API. Test with curl or Postman first, then switch the real form to VGS Collect (hosted fields, so your page's JS never touches the card either). Outbound: your backend sends the charge through VGS as an HTTPS proxy and trusts VGS's CA certificate.
    
        
    
        
    
      
    
    
    
  
    

  
    
    
    
      
    Things that trip people up
    
      most of these can be reproduced above
    
    
    
    
      
      
        
    • Filters match by condition, not by magic.Switch the form to x-www-form-urlencoded and submit again. The route expects application/json, so it doesn't match and the request goes through untouched. The real card reaches your backend, and nothing errors to tell you.
      • 
        
    • The outbound proxy terminates TLS on purpose.To rewrite an encrypted request body, VGS has to decrypt it. That's why your HTTP client is given VGS's CA cert (verify="sandbox.pem"). Without it, you get certificate errors on every outbound call.
      • 
        
    • CVC goes in volatile storage.PCI DSS doesn't let you keep the CVC after it's used. VGS's walkthrough sets the CVC filter to volatile storage, which is only good for about an hour. Charge with it right away, and remember to add a matching REVEAL filter for it on the outbound route.
      • 
        
    • Turn on payload logging while you test.In the dashboard, open Logs and record payloads. Each request then shows which filters fired, and you can see the redacted body inbound and the revealed body outbound. That's the fastest way to catch the Content-Type mismatch in #01.
      • 
        
    • The alias format is a product decision.A format-preserving alias (keeps the first 6 and last 4, passes the Luhn check) gets through your existing card validation and still shows "Visa •••• 1111" correctly. A random tok_ alias is obviously not a card, so nothing can mistake it for one.
      • 
        
    • Aliasing a field you later need breaks things.Redact the cardholder name and your backend can no longer personalize the receipt email. It only has the alias. Redact what you never need to read yourself.
      • 
        
    • It reduces scope. It doesn't remove it.Your servers stop storing and handling card data, which shrinks your PCI footprint by a lot. But the page that collects the card, your VGS credentials, and your route config still matter. VGS Collect covers the collecting page.

    Setting it up for real
    
      following VGS's own walkthrough
    
    
    
    These steps follow VGS HTTP Proxy (a quick walk through) from the VGS integration team. Its advice: set up the routes first, and leave the form until last.
    
    
    
      
      
        
    • Inbound route: Routes → Inbound → Add.Upstream is your server with the database. That's where the aliases get stored. Set the path and content type, then add a REDACT filter on the card number with persistent storage (19-digit fixed length is common) and one on the CVC with volatile storage. Docs: Inbound Routes.
      • 
        
    • Outbound route: Routes → Outbound → Add.Upstream is the third party, such as Stripe, WorldPay or Adyen. Set the path you're calling (/payments, /customers, whatever it is), then add REVEAL filters for the same fields: one for the persistent card number, one for the volatile CVC. Docs: Outbound Routes.
      • 
        
    • Logs → record payloads.Now every request shows which filters succeeded and the body before and after.
      • 
        
    • Test with curl or Postman.The dashboard gives you code snippets. Send a card to the vault URL and check that your server receives aliases. Then send the charge through the forward proxy and check in Logs that the third party got the real values.
      • 
        
    • Then build the real form with VGS Collect.Start from the vgs-collect-examples repo and the VGS Collect JS docs. Do the reveal call on your server in Python, Java, Node, or whatever you use.
